# 作業ルール（CK-Autolisp）

## 既存ファイルを更新するとき

- 上書き・変更・削除する前に、**旧データを `old/` フォルダへコピーしてから**更新する。
- 保存先は元のフォルダ構成をそのまま `old/` の下に再現し、ファイル名の先頭に日付（`YYMMDD_`）を付ける。
  - 例：`catalog/00_世界のAutoLISP総合一覧_採点.xlsx` を 2026-09-27 に更新する場合
    → `old/catalog/260927_00_世界のAutoLISP総合一覧_採点.xlsx`
- 同じ日に同じファイルを2回以上更新する場合は、`260927-2_` のように連番を付ける。
- 新しく作るファイルは対象外（旧データが無いため）。
- `old/` の中のファイルは書き換えない・削除しない。

## AutoLISP を作成するときのルール（チコさんの基準）

- **チコさんが大事にしていること（いちばん優先）**：
  1. **あらゆる環境で安定して使える**（設定・バージョン・図面の状態に左右されない。分からないときは無理に動かず、知らせて止まる）。
  2. **シンプルな仕様**（機能を盛りすぎない。基本は1コマンドで迷わず使える）。
  3. **なるべく AutoCAD LT 2024 以降でも使える形にする**（LT で使えない機能は避ける。どうしても無理なら、その理由をチコさんに伝える）。

- **対応環境**：AutoCAD 2027。
- **文字コード**：出力する LSP ファイルは、基本的にすべて **ANSI（Shift-JIS）** で保存する（テスト用の LSP も含む）。ダイアログの定義（DCL）も ANSI で書き出す（`open` にエンコードを指定しない）。UTF-8 では AutoCAD のバージョンによって日本語が文字化けする（チコさんの実機で確認）。lispcheck も UTF-8 の LSP・DCL を警告する。
- **UNDO**：UNDOグループを使い、コマンド実行前後で適切に Undo できるようにする。エラー発生時も UNDO グループが正常に終了するようにする。
- **結果の通知**：処理完了時は、処理結果（件数など）を通知する。
- **ショートカット**：正式なコマンド名とは別に、短く覚えやすいショートカットも作る。
- **システム変数**：変更した場合は、処理終了時・エラー終了時のどちらでも必ず元の値に戻す。
- **安全な終了**：ユーザー入力のキャンセル（Esc）や、何も選択されなかった場合でも、エラーで落ちずに安全に終了する。
- **環境に依存しない**：UCS の設定・UCSFOLLOW・OSMODE などの値に左右されず、どんな環境でも動くようにする。
- **command-s の使い分け**：`*error*` 関数の中では基本的に `(command-s ...)` を使う。それ以外の場所では通常の `(command ...)` でよく、`command-s` に切り替える必要は基本的にない。
- **設計の好み（操作の形）**：基本の使い方はシンプルで素早く実行できる（選ぶだけ・Enterで前回設定のまま実行など）。そのうえで、設定画面に進めば柔軟に細かく設定できる形にする（例：コマンド実行中に「設定(S)」オプションやダイアログを開ける。設定は記憶して次回に引き継ぐ）。
- **動作確認用の図面**：LISPを新しく作った・直したときは、毎回あわせて次の2つを作る（保存先は `tools/<ツール名>/test/`）。
  - 動作確認用のDXF図面：確認したいケースごとに区画を分け、各区画に見出しと「こうなれば正常」という期待結果を書く。ロック画層・非表示画層・回転・マルチテキスト・寸法・ブロックなど、不具合が出やすい条件も入れる。見出しは動かないようロック画層に置く。
  - 確認手順書（Markdown）：どの区画で何を実行し、どこを見ればよいか。
  - 大量データ（速度確認）用の図面は作らない（速度は実務図面で確認する）。
  - AutoCADでの実行確認はできないため、実行と結果の確認はチコさんが行う。
- **lispcheck での事前確認**：LISPをチコさんに渡す前に、`tools/lispcheck/lispcheck.py`（AutoCAD の簡易シミュレータ）で確認する。
  - `lint`（実行せずにチェック）→ テスト図面で `run`（確定・Esc・元に戻す・選択なし・設定変更など、主な場面を一通り）。
  - エラー・システム変数の戻し忘れ・図面の変化（比較画像）を見て、不具合があれば直してから渡す。
  - 結果は `tools/<ツール名>/test/lispcheck結果/` に「検証結果.md」と比較画像で残す。lispcheck で確かめられないこと（画面表示・ダイアログ・UCS など）は、AutoCAD で見てほしい点として書き出す。
  - lispcheck 自体の誤りに気づいたら、直した内容をチコさんに伝える。
- **公開済みの LISP を直すとき（互換性を絶対に壊さない）**：今まで使えていた人が使えなくなる変更はしない。
  - 変えないもの：コマンド名・ショートカット、質問の順番・選び方・答え方（マクロやスクリプトで使っている人がいる）、処理の結果、記憶する設定の名前・保存場所、ファイル名。
  - 直すのは「失敗したときの後始末」と「表示」を足すことが基本。Undo を閉じる処理などは、開いたときだけ閉じる形にする。
  - 直す前と後を、同じテスト図面で lispcheck にかけ、結果の図面とコマンドラインの記録を比べて、普段の動きが同じことを確かめる。違いは足したメッセージだけであること。
  - バージョンを上げ、更新履歴に「何を足したか・普段の動きは変わらない」を書く。旧版も残す。
  - 直したファイルは、ファイル名の最後に `_ver2`（次は `_ver3`…）を付ける（例：`XForce_ver2.lsp`）。公開中の版は同じフォルダに元の名前のまま残す。バージョンの表記は ver2 から付ける（初版には不要）。
  - ショートカットの無い公開済みのコマンドは、そのままでよい（新しく足さない）。今あるコマンド名・ショートカットも変えない。
- 既存のLISPを評価・解析するときも、上記を「堅牢さ」の確認項目として使う。
- **コードの見せ方**：LISP の全文は、チコさんに求められない限り返答に載せない（変更点の説明と GitHub の場所を伝える）。
- **改良の積み残し**：見つけたけれど今は手を付けない改良点は、`tools/<ツール名>/改良メモ.md` に残す。
- **note の記事の書き方**：記事は簡潔に短く書く（チコさんのポリシー）。
  - バージョンアップの説明は、使う人から見て仕様が変わった所だけを1行で書く。それ以外は「安定性を強化しました。」の一言にする。
  - 以前に不備があったように読める書き方は、特別な場合を除き避ける。
  - 新旧どちらも上げ、最新版を上に置く（「最新版をお使いください。うまく動かない場合は旧版をどうぞ。」）。
  - 見本：`tools/00_note記事更新メモ.md`
